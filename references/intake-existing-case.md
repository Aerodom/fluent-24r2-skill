# 接手一个别人给的算例（任何中间状态）

> 从零搭是少数，**接手半成品是多数**。「给你一个 Fluent 算例，在这个基础上改」——
> 可能只给了几何，可能网格建好了没设边界，可能设置全了但跑飞了，
> 也可能跑完了却只有几张截图。本节解决的就是"从哪里下手"。

两种错误做法，都要避免：

| 错误做法 | 后果 |
|---|---|
| **推倒重搭** | 丢掉对方全部的物理判断（材料、边界量级、模型选择），并且把已知的坑再踩一遍 |
| **直接在原件上改** | 对方的东西毁了，出了问题没有对照基准；改坏了连"原来能跑吗"都无从回答 |

正确目标：**先搞清它现在到底处于什么状态，再把缺的那一段补上**。

---

## 1 第一步不是打开 Fluent，是盘点

```bash
<venv>/Scripts/python.exe scripts/inspect_case.py <算例目录> --out triage.md
```

**离线读 `.h5`**（h5py），不启动 Fluent、不占 license、不占内存，几秒出报告。
报告八节：资产清单 / 身份 / 网格 / 区域清单 / 场与时间 / 收敛证据 / 告警 / 建议接续点。

为什么必须先离线做这一步：接手时最贵的是**误判**。开 Fluent 看面板要 1 分钟起停、
要 license、还要人眼逐面板翻；而"有几个 zone、什么类型、有没有 data、上次收敛没有"
这些决定性事实，在 `.h5` 里全都躺着。

脚本的红线：**读不到就写"读不到"**。区域类型码只收本机实测过的值，其余标 `?`；
`unknown` 会明确让你去面板确认，不按邻居猜。这条红线比"报告漂亮"重要得多。

## 2 资产 → 阶段：接手的第一张表

拿到东西先对号入座，再谈别的。

| 收到的东西 | 大概到哪 | 从哪接 | 第一件要确认的事 |
|---|---|---|---|
| 只有 CAD（`.step` / `.x_t` / `.igs`） | 无 | **P1** | 单位！量一下包围盒（`troubleshooting` M） |
| 网格 `.msh.h5` / `.cgns` / `.msh` | P1 | **P2** | 网格能否分辨特征尺度（铁律 4）；zone 是否被合并 |
| `.cas.h5`，无 `.dat.h5` | P1 P2 | **P3** | t=0 初始场（patch 量对不对） |
| `.cas.h5` + `.dat.h5`，未收敛 / 跑崩 | P1–P3 | **P3 诊断** → 修 → P4 | 见 §5 诊断顺序 |
| `.cas.h5` + `.dat.h5`，已收敛 | P1–P4 | **P5** | 口径对不对（起算基准、阈值来源） |
| **只有 `.dat.h5`** | — | **P2（先要 case）** | ★ 见下面"最坏的情况" |
| 只有几张图 / 一份报告里的数字 | 无 | **P0 重定口径** | 无法接手，只能复现；口径必须自己重新立 |
| 只有 `.jou` / `.wbjn` 脚本 | 不定 | **先跑一遍看它到底做了什么** | 脚本可能早就和 case 不一致了 |
| 有 `.wbpj` 但打不开 / 拷到别机失效 | P1–P6 | **P6 修** | 见 §8 的可搬移四步法则 |
| 一堆 `.trn` 日志 | 不定 | **先读日志**（最硬的证据） | 它上一次到底跑到哪、为什么停 |

### 最坏的情况：只有 `.dat.h5`

**2024R2 的网格在 `.cas.h5`，场在 `.dat.h5`**（§7.1 坑 1）。所以只有 data 时：

- 离线后处理**做不了**（没有单元形心、没有面拓扑、没有 zone 定义）；
- 续算**做不了**（没有模型设置）；
- 只剩一件事：**把 case 要回来**。别急着写脚本去硬解 dat。

体检脚本会直接把这种情况标成 P2 阻断，就是为了拦住"在 dat 上瞎折腾"这条弯路。

### 只有别人的结论数字（论文/报告/PPT）

这时不存在"接手"，只有"复现"。必须**自己重立 P0 口径**，并明确写下：
对方的数字是哪个量、从哪起算、什么时间窗、阈值谁定的。
拿不到这些就问 —— 猜出来的口径做出来的复现，对不上也没法说是谁错。

## 3 五个问题：接手前必须能回答

回答不了就别动手。

1. **它要什么？** 终态是什么、验收量是什么、口径谁定的。
2. **它现在到哪了？**（§2 的表 + 体检报告）
3. **它上一次跑成什么样？**（转录 + 残差历史 + 文件时间线，三个互相印证）
4. **它缺什么才能交付？** 列成缺口清单，逐项标"谁补、怎么验"。
5. **要改哪里？** 只能写"被证据证明有缺陷的那一处"，不能写"我觉得这里可能有问题"。

第 5 条是分水岭。接手最常见的翻车方式不是改错，是**顺手改了一堆没证据的地方**，
最后出问题分不清是自己的改动还是原有缺陷。

---

## 4 三条铁律

1. **原件只读。** 任何改动先复制，新文件新名字。原文件名与目录**不要改** ——
   case 内部记着路径（`data` 里就有 `case-file` 的绝对路径），改名会让配对关系断掉。
2. **不要重搭。** 能证明原设置错在哪，就只改那一处。重搭等于把对方所有物理判断退回原点。
3. **先看证据，再动手。** 证据优先级：
   **`.trn` 转录 > 残差历史 > 文件时间线 > 对方口头描述**。
   口头描述经常是"我记得应该设了"，而转录不会记错。

---

## 5 "跑过但没跑通"的诊断顺序

按顺序走，别跳步。跳步的代价是把设置问题当网格问题，然后把网格重画一遍。

| 步 | 看什么 | 判据 / 结论 |
|---|---|---|
| 1 | `.trn` 末尾 30 行 | 有 `solution is converged` → 它其实跑通了；有 `Fatal` / `Error:` → 直接跳到对应条目 |
| 2 | 残差历史（体检报告第 6 节） | `NaN/Inf` → 发散（`troubleshooting` C）；末段在**上升** → 发散；一直在降但没到判据 → 只是没跑够 |
| 3 | 进程与内存 | 日志停在第一步、CPU 满但不出 `Flow time` → 八成 OOM（§9，看**提交内存**不看物理可用） |
| 4 | 文件时间线 | `case` 比 `data` 新 → data 是过期的；网格比 case 新 → zone ID 可能已重排 |
| 5 | 包围盒量级 | 尺寸差 1000 倍 → 几何单位错（`troubleshooting` M） |
| 6 | 单元区域类型 | 是 `solid` → "Flow boundary zone found adjacent to solid zone"（`troubleshooting` P） |
| 7 | 边界类型与量级 | 没有 in/out、或入口速度差几个量级 → 设置问题 |
| 8 | 才轮到网格质量 / 格式 | 最小体积为负、负体积、长宽比极端 |

**第 3 步容易被跳过**，因为"卡住不动"看起来最像发散。实测过两次都是内存：
第 1 步 CPU 满负荷但长时间不输出 `Flow time`，清残留进程 / 等内存释放后立刻正常。

### 症状 → 先查哪儿

| 症状 | 最可能 | 先看 |
|---|---|---|
| 一启动就退出，`exit=1` | 编码 / license / 残留进程 | 日志末尾是否 `UnicodeEncodeError`；`cx2420.exe` 是否残留 |
| 第 1 步长时间无 `Flow time` | 内存不足；或求解 journal 里有 point-surface | §9 提交内存；journal 里搜 `point-surface` |
| 残差漂亮但物理荒谬 | 单位、边界量级、材料赋值 | 包围盒；phase 材料是否真的改上了 |
| 跑到一半静默消失 | 进程被整棵杀掉 | 是否由会话内拉起（须外部周期拉起） |
| 续算报 `mesh has been modified` | 改过 zone 类型而 case 没重存 | 改完 zone 立刻 `write-case` |
| 交付指标整列恒为 0 | 该量依赖的 BC 类型不对 | 回去查它依赖的 Dirichlet 条件 |

## 6 六个高发陷阱（都来自真实接手）

1. **版本回流。** 对方用 19.x / 2024R1 写的 case，24.2 能读**不代表**没静默改设置。
   接过来先跑 `references/version-compatibility.md` 的六项探针。
2. **UDF。** case 引用了编译 UDF（`libudf`），没有源码 / 编译库就跑不起来；
   或者更糟 —— 库还在，但 ABI 不兼容静默生效成错的值。
   查：case 目录有没有 `libudf/`；`.trn` 里搜 `Loading library`。
3. **路径硬化。** case 里记着绝对路径（data 的 `case-file`、UDF 库、profile 文件）。
   换机后要么重建配平，要么确认路径存在。体检报告第 5 节会把记录的路径打出来。
4. **zone ID 重排。** 重导网格后 ID 会变，绑在 ID 上的边界条件、register、监控点全部错位。
   症状：边界条件"设了但没生效"。
5. **改 zone 类型即改网格。** 之后所有 autosave 都无法续算（硬规则 2）。改完立刻存 case。
6. **区域名无意义。** 导入自动生成的名字可能是
   `freeparts-open-cascade-step-translator-7.8-1` 这种；`sep_face_zone_angle` 拆出来的
   子区叫 `...:1:005`。**认 ID，不认名字。** 名字只用来给人看。

## 7 增量改造：改什么就回哪一段

接手后最常见的需求是"在现有基础上加一点东西"。按改动性质回退到对应阶段：

| 想做的事 | 回哪 | 要不要重建 case | 备注 |
|---|---|---|---|
| 换交付口径（量、切片高度、时间窗） | P5 | 不用 | 纯后处理，动脚本即可 |
| 只让它多跑一会儿 / 收敛更好 | P4 | 不用 | **续算，不要从头重跑**（§4.2） |
| 改边界条件数值 | P2 | **要** | 改完立刻 write-case |
| 改边界条件类型（wall → inlet） | P2 | **要** | 类型变化改的是 zone 定义 |
| 层流 → 湍流、加能量方程 | P2 + P3 | 要 | 网格要求变了，先按铁律 4 重估 |
| 加 VOF / 加组分输运 | **P1 重估** | 要 | 换物理 = 换网格要求，原网格通常不可复用 |
| 换网格 | P1 全走 | **必须** | zone ID 会重排，所有 ID 相关设置重设 |
| 只补 `.wbpj` | P6 | 不用 | 见 §8 |

判据很简单：**改动是否改变了"网格被解释的方式"**。改了就要重建 case，
因为 case 里存着 zone 的类型与边界定义，这些是按 ID 绑在具体网格上的。

## 8 接手后必须留下的两样东西

1. **一份改了名的副本**，名字带来源与日期：
   `<原名>_v2_<来源>_<YYYYMMDD>.cas.h5` / `.dat.h5`。
   这样三个月后能回答"这版是谁改的、从哪儿改的"。
2. **一份体检报告 + 改动清单**：改了哪几处、每处的证据是什么、用什么判据验证的。
   这份东西就是以后的"为什么这么设"。没有它，下一个接手的人（可能是你自己）
   还得从头猜一遍。

## 9 与主流程的关系

接手**不是**另一套流程，是**从中间插进 §3 的 P0–P7**：

```
盘点（§1）→ 定锚点（§2）→ 从该阶段起走 §3 的闸 → 到 P6 交付 → P7 回写案例
```

- **P0 不要无脑重定。** 原口径若可考（有 README、有报告、有对方说明），
  直接沿用并在文档里写"沿用自 X"，把精力留给真正缺的部分。
  只有当原口径不可考、或明显不成立时，才重定并写明为什么。
- **锚点之后照常过闸。** 接手最容易犯的错是"反正前半段是别人做的，跳过闸"。
  恰恰相反 —— 别人的前半段没经过你的闸，**更要验**。

## 附：本机实测的两个读文件口径（踩过才知道）

1. **残差数组的列不是"迭代/残差/…"**。`results/residuals/<方程>/data` 是四列：
   `[未归一化残差, 归一化因子, 0, 0]`，Fluent 打印的是**两者之商**。
   实测核对：continuity 末行 `6.953693e-07 / 7.411549e-04 = 9.3822e-04`，与转录
   `39  9.3822e-04` 逐位吻合。**直接把第 0 列当残差会小三个量级**，
   从而把"没收敛"报成"收敛得漂亮"。
2. **`cellType` 不是 `zoneType`**。`zoneType` 才是 fluid / solid 区域类型；
   `cellType` 是**单元几何形状码**（本机实测多面体 = 7）。
   `.msh.h5` 里只有 `cellType` 没有 `zoneType` —— 说明网格还没被求解器定型，
   这是正常状态，不是"区域类型未知"。

这两条都写进了 `scripts/_common.py` 之外的体检脚本注释里，
改脚本时**别推翻**，推翻就是把两个静默错值装回去。
